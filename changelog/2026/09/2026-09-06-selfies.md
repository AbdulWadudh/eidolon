# Selfies: real image generation through ComfyUI and PuLID

**Date:** 2026-09-06
**Scope:** apps/conductor, apps/canvas, packages/config, packages/protocol

## What it was

Image generation existed as a shape, not a feature. `request_image` sent a
`painting` status, posted a hardcoded SDXL-Turbo workflow at ComfyUI, ignored
the result entirely, then emitted a 60-byte base64 `image_preview` and an
`image_ready` pointing at a mock backdrop URL. The workflow named
`sd_xl_turbo_1.0_fp16.safetensors`, which is not the checkpoint installed, so
even the queue call would have been rejected on validation. On the client the
gallery button was wired to a no-op and no message could carry an image.

## What it is

Tapping the gallery button asks the character for a photo. The character sends
one back, in the chat, of the same person every time.

**The face is bootstrapped once and then reused.** PuLID needs a reference face,
and no character had one. The first request asks the LLM to turn the character's
written persona into a physical description, generates a plain portrait from it,
and stores that as the character's avatar in S3. Every later photo runs
`ApplyPulid` against it, so identity survives across scenes, outfits, lighting
and restarts. The description is stored on the character too — regenerating it
per process gave Emma brown eyes one run and blue the next, which contradicted
the face PuLID was matching.

**The scene comes from the conversation.** `image.scene` turns the last turns
plus whatever was asked for into an image prompt. The physical description is
prepended in code rather than asked for again, since asking produced it twice in
the same prompt.

**Two prompts, one catalogue.** `image.appearance` and `image.scene` join the
other eight in `@eidolon/config`, editable in one place like the rest.

## The roleplay model will not write prompts

Asked plainly for an image prompt, the model replied in character:

```
FULL PROMPT:
*looks up from my phone with a smile, seeing it's you* Hey there! How was your day?
```

It is tuned to be a person, and a bare instruction reads as dialogue. Two things
fix it: a system message that frames the job as writing prompts and forbids
first person and asterisks, and a guard that checks the output actually looks
like a prompt before trusting it. `isPromptLike` rejects asterisks, quotes,
questions and first or second person; anything rejected falls back to the
reader's own words for the scene, and to a fixed description for the appearance.
The generation never fails because the model went method.

## The pipeline

`services/comfy-workflow.ts` builds the graph — twelve nodes with PuLID, seven
without, so a character with no face reference yet still renders. Sampler
settings come from `IMAGE` in the config: RealVisXL V5.0 Lightning at 6 steps and
CFG 2, which is what a Lightning checkpoint wants, against the old stub's 25
steps and CFG 7.

`services/comfyui.ts` was rewritten from a fire-and-forget POST into a real
client: upload the face reference to ComfyUI's input directory, queue the graph,
poll `/history/{prompt_id}` until it completes, pull the PNG from `/view`, and
hand back bytes. Failures are typed — `ComfyUnavailableError` when the server is
not there, `ComfyGenerationError` when the graph fails — so the socket can say
"No camera on this side" rather than dropping a mock image into the transcript.

## Timings, measured

| | |
|---|---|
| plain SDXL portrait | 3.9s |
| first PuLID run | 48.1s |
| warm PuLID run | 5.3s |
| full round trip, first ever request | 16.5s |
| full round trip, warm | 5.5s |

The 48s is PuLID, EVA-CLIP and InsightFace loading into VRAM on first use. It is
paid once per ComfyUI process, and the first request for a character pays the
face bootstrap on top, which is why the first round trip is 16.5s and every one
after is about five.

## Client

`messages.image_url` and `characters.appearance` are new columns, both added
through the same idempotent `PRAGMA table_info` check as `audio_duration`.
`image_ready` appends an assistant message carrying the URL, and the transcript
returns it, so photos survive a reload the same way voice notes now do.

`MessageImage` renders inside the bubble at the generated aspect ratio, with the
theme's radius and card border, and a shimmer underneath until the bitmap
arrives. It uses `expo-image` for disk caching and a cross-fade — added on
request, at the SDK-pinned `57.0.4`.

## Still open

- `image_preview` is defined in the protocol and never sent. ComfyUI streams
  progress over its own websocket; the conductor polls history instead, so there
  is no step counter behind "Taking the photo".
- Nothing cancels a queued ComfyUI job. `interrupt` aborts the wait, not the
  work.
- The photo is not tappable. There is no full-screen viewer.
- `forgetCharacter` leaves the avatar and appearance in place, so resetting a
  character's memory keeps their face. That is deliberate, but it means there is
  no way to ask for a different face short of clearing the columns by hand.

## The photo button asks first

Tapping the image icon fired a request immediately. It now opens a sheet that
asks two things in order: how the photo should be framed, then what it should be
of.

Orientation is a deliberate choice rather than a guess. The shot planner returns
an orientation and there is a keyword fallback behind it, but both were wrong
often enough — "the view from your window" came back upright — that guessing was
not good enough. `request_image` carries an explicit orientation now and the
reader's choice wins over both.

The situation step is optional. Four ideas drawn from the conversation arrive as
chips from `request_photo_ideas`, tapping one fills the field, and the field can
be edited or left empty for her to decide.

## Watching it happen

ComfyUI streams progress over its own websocket, so there is no reason to show a
spinner. `PaintingCard` takes the place of the reply card from the moment the
request is sent: a shimmering frame at the photo's aspect ratio, the current
stage, a progress bar and `3 / 6`. It clears on `image_ready` **or**
`image_failed` — the failure event exists so the loader cannot hang when
generation dies, which it did when ComfyUI ran out of VRAM mid-session.

## Photos are objects you can act on

Tapping a photo opens it full screen. Pinch to zoom to 4x, drag to pan once
zoomed, double tap to toggle. Underneath: set it as the character's profile
picture, set it as the chat background, regenerate, or delete.

The avatar and background persist on the character (`avatar_url`,
`background_url`) and come back with the transcript, so they survive a reload.
The background sits behind the whole screen at `PHOTO.backgroundOpacity`, low
enough to stay out of the way of text. Setting a new avatar clears the cached
face reference, so the next photo is matched against the picture you chose.

## Captions are best effort

The character sends a line with the photo. Getting that line out of a 7B roleplay
model turned out to be the hardest part of this change, and it is still only
right about half the time.

It writes monologues (`*looks at cat photo* this is what I've been reduced to...`),
answers as the person receiving the photo (`why did you send me this pic?`),
narrates the frame (`The photo shows my cat on the couch`), or answers the
question about the task instead of doing it (`Here is a message I might send`).
Constrained decoding made it worse rather than better — asking for
`{"caption": string}` at a 44 token budget produced nested JSON and, once, the
string `#)`.

So the caption is generated, then checked, and dropped when it fails. A photo
with no caption is an ordinary thing to send; a photo captioned "#)" is not.
`usableCaption` requires three to fourteen real words and rejects brackets,
asterisks, third person, frame narration and meta answers. Nine cases are pinned
in `tests/caption.test.ts`.

Two things that were not the model's fault. The caption was originally a field on
the shot schema, generated under a system prompt reading "you never use first
person" — a caption is inherently first person, so constrained decoding had
nothing valid to emit and returned an empty string every time. And the shot JSON
was being truncated at 220 tokens, which silently failed the whole parse.

## Framing the profile picture, and the background left alone

Three follow-ups after the first look.

**The background was being dimmed.** It rendered at `PHOTO.backgroundOpacity`
so text stayed readable over it. That was a decision the reader had not asked
for — a background you chose should look like the picture you chose. It renders
at full opacity now and the constant is gone.

**A profile picture is a crop, not a whole photo.** Tapping "Profile picture"
used to take the photo as it was, which for a landscape shot of two people at a
beach meant an avatar of nobody in particular. It now opens a circular frame you
drag and pinch, and only what is inside the circle is used.

No image is cut. The crop is stored as `{zoom, offsetX, offsetY}` on the
character, with the offsets normalised against the frame so they survive
different screen widths, and applied as a transform wherever the avatar is
drawn. That keeps the original photo intact, needs no image-processing
dependency, and means the crop can be changed later without regenerating
anything. It does not affect the face reference either — PuLID runs InsightFace
over the picture and finds the face itself, so a decorative crop would have been
wasted work there.

**Tapping the profile picture opens it.** Full screen with the same pinch and
pan as any other photo, minus the action row — `showActions={false}`, since
"set this as your profile picture" is not a useful thing to offer about the
profile picture.

## One command to bring the stack up

Three separate services died mid-session — the LLM twice, ComfyUI twice, once
taking the captions down silently because `askInVoice` returns an empty string
rather than throwing. Finding that meant checking three ports by hand every
time.

`bun run stack:status` prints all five in one go, and `bun run stack:up` starts
whatever is not running and waits for each to answer its health endpoint before
moving on:

```
  [ok] llm        http://127.0.0.1:8080/v1/models
  [ok] tts        http://127.0.0.1:8880/v1/models
  [ok] comfyui    http://127.0.0.1:8188/system_stats
  [ok] storage    http://127.0.0.1:9000/minio/health/live
  [ok] conductor  http://127.0.0.1:3000/health
```

Timeouts are per service, because they are not comparable: ComfyUI takes minutes
to load its models, the conductor is up in seconds. Storage is marked optional —
it comes from `docker compose`, which this script deliberately does not drive.
`EIDOLON_AI_ROOT` points at the servers if they are not at `G:\AI\EIDOLON`.

## Watching the photo develop

The loader showed a bar and a step count. ComfyUI is already sending the actual
image as it denoises, so there was no reason to show anything less.

Those frames come over the same websocket as the progress events, as binary
rather than JSON: an eight byte header — event type, then image format — and
then a JPEG. They carry no prompt id, so they are routed to whichever prompt last
announced it was executing. `PaintingCard` draws the latest one behind the
progress bar, and the shimmer only runs until the first frame arrives.

Measured on a six step generation: six frames, 55kb to 77kb each, one per step,
the first at 11.4s and the last at 14.1s with the finished photo at 15.1s. Over a
LAN that is nothing, and it is the difference between a progress bar and watching
it happen.

## Gestures never worked inside the viewer

Pinch to zoom and the crop drag both did nothing, for the same reason: a React
Native `Modal` is a separate native view hierarchy, outside the
`GestureHandlerRootView` at the app root. Gesture Handler has nothing to attach
to in there, so every gesture is silently ignored — no error, no warning, just a
picture that will not move.

The viewer wraps its own `GestureHandlerRootView` now. Worth remembering: any
gesture inside a `Modal` needs its own root, and the failure mode is silence.

## A bad avatar url broke every photo after it

`ensureFaceReference` fetched the stored avatar with no error handling, so an
unreachable URL threw and the whole generation failed. Any avatar set from a
photo that is later deleted, or set while storage is down, would have poisoned
every photo from then on with "That photo did not come out".

It falls back to generating a fresh portrait now. Found by pointing an avatar at
a URL that does not exist while testing the look endpoint, which is exactly how
a reader would hit it.

## Save to device

A fourth action in the viewer. The photo is fetched, written to the cache
directory, handed to `MediaLibrary.saveToLibraryAsync` and the temporary file
deleted. Permission is requested at the point of use rather than on launch, and a
refusal says so rather than failing silently.

This needs `expo-media-library`, which links native code — a JS reload will not
pick it up, it needs the APK rebuild.

One trap on the way in: `expo-media-library@57.0.4` appeared to be a broken
package, with Metro unable to resolve `./types/SortDescriptor` from a file that
plainly exists on disk. It was a stale Metro resolver cache from before the
install. `expo export` bundles all 2611 modules cleanly after clearing it.

## You could not see what you were cutting off

The crop screen drew the photo only inside the circle, with black around it. So
the one thing a cropper exists to show — what falls outside the frame — was the
one thing it hid. Dragging felt like the image was being destroyed rather than
framed.

It draws the whole photo now, dimmed to `PHOTO.cropDimOpacity`, with the circle
as a bright window onto the same picture. Both layers are the full working width
and share one transform; the clipped one is pulled back by the inset so their
centres coincide, which is what makes them pan and zoom as a single image rather
than two that drift apart.

That changes the arithmetic. The photo is now drawn across the whole width while
the avatar fills its container edge to edge, so the saved crop carries the ratio:
`zoom` is `(side / circle) * pinch` and offsets are normalised against the circle
rather than the screen. At rest that is a zoom greater than one, which is correct
— the ring only ever showed the middle of the picture. Four cases are pinned in
`tests/avatar-crop.test.ts`, including that two screen widths produce the same
crop.

## The profile picture is a photo too

Tapping it opened a viewer with no actions at all, on the grounds that offering
"set as profile picture" for the profile picture is silly. That threw out the
two that do apply. It now offers **Adjust framing** and **Save to device**.

`showActions` became `actions`, a list, so each viewer says what it offers rather
than choosing between all or nothing. `adjust` and `avatar` both open the crop —
they differ only in whether the picture being framed is already the avatar. The
hook reads `viewing?.imageUrl ?? avatarUri`, so save and crop work from either
entry point, while delete still requires a message to delete.

## The crop was two images, and Android only clipped one

The first attempt drew the picture twice: a dimmed copy, and a bright copy
clipped to a circle. On a device the bright copy rendered in full, straight over
the dimmed one and the buttons, offset from it — the frame showed one part of the
photo while the screen showed another.

Android does not reliably clip a **transformed** child to a rounded parent.
`overflow: "hidden"` with a `borderRadius` is honoured for static children and
quietly ignored once a transform is on the child, which is exactly what a
pan-and-pinch cropper does.

So the picture is drawn once now, and the dimming is a mask over it: a single
view with a border thicker than the screen and a fully round radius leaves a
transparent disc in the middle and covers everything outside it. Nothing is
clipped, so there is nothing for the platform to get wrong, and the bright area
is by construction the same pixels as the dark one.

## Saving works in Expo, without a rebuild

The advice up to now was "install the new APK", which is no help when the app is
being run through Expo. It was also unnecessary.

`expo-media-library`'s package root is the new *Next* API. It imports
`ExpoMediaLibraryNext` at module scope and builds classes out of it, so on any
client without that native module the import throws — and since this module is
reached from the chat route, that throw took the route down with it. That is
what `Route "./(main)/chat/[id].tsx" is missing the required default export` was
reporting, and why the button then failed with `undefined is not a function`.

The package also publishes `./legacy`, backed by the older `ExpoMediaLibrary`
native module that Expo Go ships, with the same `requestPermissionsAsync` and
`saveToLibraryAsync`. Importing that instead means saving works in Expo now
rather than after a rebuild.

The import stays lazy and the exports are still checked before use, because a
client with neither module leaves them undefined rather than rejecting — a
`try`/`catch` around the import never fires.

## The cropper was cutting the photo before a finger touched it

Two faults, and the first one made the second hard to see.

The working image was drawn `contentFit="cover"` inside a square. A portrait
photo in a square box loses its top and bottom to that, so the picture was
already cropped when the screen opened — before any dragging. It is `contain`
now: the whole photo is on screen, letterboxed if it has to be, and the circle
picks a part of it. The avatar switches to `contain` too when a crop is stored,
because the two have to lay the image out the same way or the avatar shows
something other than what was framed. Without a crop it stays `cover`, so an
untouched avatar still fills its circle.

Nothing responded to a drag because the chrome was covering the gesture surface.
The title and buttons were flow children with a `flex-1` spacer between them,
and that spacer sat over the middle of the screen — exactly where the circle is.
`pointerEvents="box-none"` on it was not enough. The gesture view is the flex
child now and the chrome is absolutely positioned over it, so only the buttons
themselves take a touch. The gestures are also memoised rather than rebuilt on
every render, and the gesture view is `collapsable={false}` so Android keeps a
real view for the handler to attach to.

## The crop is a region of the photo now, not a transform of a box

Framing a face and getting an avatar with black down one side was not an
off-by-a-bit: the model was wrong. The crop was recorded as a zoom and an offset
applied to a *square box*, and the photo was fitted into that box before any of
it happened. `cover` cut a portrait photo's top and bottom off before a finger
touched the screen; `contain` letterboxed it instead, and since the ring is
wider than a letterboxed portrait, the black bars were genuinely inside the
circle. Neither could be fixed by adjusting numbers.

The photo is laid out at its own aspect ratio now, as large as fits, and the
crop is written down as the circle expressed in the photo's coordinates:

```ts
{ cx, cy, widthRatio, heightRatio }
```

Where the circle's centre falls on the picture, and how many circle-widths the
picture spans. The avatar rebuilds it with arithmetic rather than a transform —
draw the photo at the size that makes the circle exactly the avatar's width,
then move it so that centre lands in the middle. Both ratios come from the same
picture, so the box keeps its aspect and nothing is squashed.

Five cases pin the round trip, including that a phone twice the size records the
same crop. Rects saved in the old format are ignored on read rather than
misapplied.

The dimming is four bands and four corner wedges rather than one view with a
border thicker than the screen — that renders inconsistently at this size on
Android, and left the lower half of the screen undimmed.

## A missing "://" that looked like it had saved

Setting a chat background appeared to work and was gone on the next visit.

`characterLookUrl` and `characterMessageUrl` were written by copying the shape
of the helpers beside them without checking what `httpScheme` returns — it gives
`"http"`, and the existing helpers add `"://"` themselves. Both of mine
interpolated it directly, producing `http192.168.1.39:3000/...`.

`fetch` reports that as "Unable to connect", `saveLook` catches it into
`lastError`, and the optimistic update it had already applied stayed on screen.
So the app showed the new background, said nothing, and had written nothing.
Deleting a photo went through the same broken URL.

`tests/character-urls.test.ts` now checks every character URL has a scheme
separator, keeps TLS when the host asks for it, escapes the id, and points at
the versioned API.

## Previews were arriving and being thrown away

The client had a `paintingPreview` field, the conductor was sending frames, and
nothing joined them: the branch that stores a frame never made it into
`chat-events.ts`. Worse, preview frames carry `step: 0`, so each one was
resetting the progress bar to zero as it arrived.

Verified: 28 preview updates reach the store in one generation and the bar never
goes backwards.

## Captions were being judged on a sentence the model had not finished

The caption is a paragraph the token budget cuts off partway through, and it was
being judged line by line — so a good caption was thrown away for words the
model never got to write. *"Hey! Looks like Mittens is lounging on my sofa
today."* was rejected because the truncated tail after it pushed the line over
the word limit.

`firstCaption` takes whole sentences up to the budget and drops a truncated last
one. The budget went to 72 tokens so sentences finish, and the whole thing is
attempted up to three times, because a small roleplay model gets this right well
under half the time and asking again costs a few dozen tokens.

Two consecutive photos now: *"You beat me to it!"* and *"Whoops! I just spilled
my wine on the carpet over there."*

## Media is grouped by character, not by kind

Keys were `images/characters/<id>/…` and `audio/<id>/…`, which split one
character's media across two trees. They are under one prefix now:

```
characters/<id>/images/<uuid>.png
characters/<id>/images/face.png
characters/<id>/audio/<messageId>.mp3
```

Everything a character owns can be listed or removed in one sweep. URLs already
written to the database are absolute, so nothing moves and nothing breaks.

## Choosing the face

PuLID matched against the avatar, which meant the picture that looks best small
was also the one every future photo had to resemble. Those are different jobs.
**Use as her face** in the photo viewer sets a face reference of its own, kept in
`characters.face_url` and preferred over the avatar. Setting it clears the cached
reference, so the next photo uses it.

## The card sat at 6 of 6 with the picture already done

Generation finished, the last preview frame was on screen, and the card stayed —
because the caption was asked for *after* the image, and three language model
calls take a few seconds with nothing to show for them.

The caption only needs the subject, which is known before the first step is
sampled. Both run together now.

## The background covered the whole screen

It sat behind the top bar and the input dock as well as the messages. It is
behind the message list only now, so the chrome stays legible over whatever
picture was chosen.

## Two smaller things

The progress bar, stage and step count moved from the middle of the card to a
strip along the bottom, over a scrim — a centred label covers the part of the
picture worth watching.

The photo request sheet is a `Modal`, which sits outside the provider wrapping
the chat screen, so the description field opened underneath the keyboard. It
does its own avoidance now. And "Refresh" joins the actions sheet, which reloads
the transcript without resetting anything.

## Regenerate edits the photo now

It asked for a fresh picture and kept only her identity, which is not what
"regenerate" reads as. It starts from the photo you were looking at.

`request_image` carries a `reference_url`; the conductor fetches it from storage
— rather than trusting a URL from the client — hands it to ComfyUI, and the
graph swaps `EmptyLatentImage` for `VAEEncode` of that picture with a denoise of
`IMAGE.editDenoise` instead of 1. PuLID still applies, so identity holds on top
of the composition that was already there. A reference that cannot be fetched
falls back to a fresh photo rather than failing.

An edit also writes a leaner prompt. Re-describing the place, the light and the
framing only fights a source image that already has them, so what was asked for
leads and the rest is dropped.

Verified end to end: a kitchen photo, then "wearing a bright red leather jacket"
against it — same kitchen, same window, same pose, jacket added.

## Two things that made edits come out wrong

The stored appearance was a run of bare fragments — `bright green` meant her
eyes, and the image model read it as a loose colour and produced green trousers.
Each detail is labelled with what it describes now (`blue eyes`, `pale skin`,
`slender build`), and appearances written before the field trimming was fixed
were cleared so they regenerate.

## The card could paint forever

A photo and a reply both end with an event from the conductor. If the socket
drops while one is in flight — a restart, a dropped network — that event never
arrives and the card sits there indefinitely. Four minutes of "Finding the
light", in the case that turned this up.

Losing the connection now ends the turn: painting and streaming stop, the status
returns to idle, and the reader is told the connection went rather than being
left watching a bar that will never move.

## A fade at both ends of the backdrop

The chat background ran flat edge to edge, so bubbles and the dock sat directly
on a photograph. The canvas colour is washed back into it at the top and bottom
over `PHOTO.backdropFadePercent` of the height, so the picture is still there
while the ends of the screen settle into the theme. `expo-linear-gradient`,
which Expo Go ships, so it needs no rebuild.
